# 新功能文档交付规范

当开发**新功能**（新增页面 / 路由 / API / 重要业务改动）时，**必须与代码同批交付「三件套」文档**，缺一不可。这不是可选步骤。

## 1. 判定是否触发

- **触发**：新增页面/路由、新增 API 接口、新增业务模块、用户明确说"新功能/新需求/做个XX页"。
- **不触发**：修 bug、改文案/样式、调配置、纯重构、加注释、装依赖。

> 拿不准时，问用户一句："这次改动需要出三件套文档吗？"

## 2. 三件套内容

| 文件 | 必含章节 |
|------|----------|
| `requirement.md` | 背景、目标、用户故事、功能范围（含/不含）、数据来源、页面/接口结构、交互需求、入口与权限、非功能需求、验收标准 |
| `development.md` | 技术栈、目录与改动清单、组件/模块结构、数据流、字段映射、扩展机制、样式/约定要点、已知限制、验证命令 |
| `test.md` | 测试范围、环境、前置条件、**测试用例表**（编号/用例/前置/步骤/预期/优先级 P0~P2）、回归清单、缺陷记录模板 |

## 3. 存放位置（固定）

```
docs/feature/<功能名-英文kebab>/
├── requirement.md
├── development.md
└── test.md
```

- 文档语言：**中文**（技术字段/接口名/路径保留英文）。
- 测试形式：**手工用例表**（项目当前无自动化测试框架；若要引入需先向用户确认）。

## 4. 执行流程

1. **先出骨架**：动手写代码前，先把三件套的骨架（章节标题 + 数据来源 + 验收标准）落到 `docs/feature/<name>/`，让用户确认方向。
2. **边开发边补**：开发文档与代码同步写，不要"先写完代码再补文档"。
3. **测试用例先行**：`test.md` 的核心 P0 用例要在开发中就写好，作为开发自测依据。
4. **交付前自检**：对照 `test.md` 回归清单跑一遍，确认三件套齐全且 `pnpm ts-check` 通过。

## 5. 参考范本

`docs/feature/weekly-board/` 是第一个完整三件套，作为后续所有新功能的**模板范本**。新功能的三件套结构与它保持一致。

## 6. 与 AGENTS.md 的关系

`AGENTS.md` 里有同名的「文档交付规范」章节作为兜底常驻提示。本 skill 是它的**详细执行版**，触发时以本 skill 为准。
