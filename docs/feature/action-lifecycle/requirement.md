# 行动项闭环与多端支持 需求文档

> 版本：v1.0  ·  状态：规划中（待评审）
> 涉及：行动项提出人识别、完成闭环、移动端支持
> 关联代码：`mytasks/`、`meeting/[id]/`、`api/actions/`、`api/chat/`、`layout.tsx`、`dashboard-layout.tsx`

---

## 一、背景与三大问题

当前会议纪要系统在「行动项生命周期」上存在三个核心缺陷：

| 问题 | 一句话描述 | 现状根因 |
|------|-----------|---------|
| 问题1 | 行动项「提出人」默认填成会议创建人/主持人，而非真正提出该事项的人 | AI 提取流程不识别提出人，代码用 organizer 兜底（`generate/route.ts:77-96`） |
| 问题2 | 没有「闭环」概念——责任人 B 完成后，提出人 A 完全不知情 | 完成回传只写库，全仓无任何「通知提出人」逻辑 |
| 问题3 | 仅支持 Web，无法在手机/小程序使用 | 纯 Next.js Web，无 viewport、无 PWA、无小程序（`layout.tsx` 缺 viewport 导出） |

---

## 二、问题1：提出人识别

### 2.1 现状根因（已验证）

- AI 提取行动项的主流程 `lib/minutes-derive.ts` **不提取 proposer 字段**。
- 默认值链路：`用户生成时指定 → 会议级 defaultProposer → 会议组织者 organizer`。
- 即：不指定就默认填主持人，与真实提出人经常不符。

### 2.2 需求目标

行动项的「提出人」应反映**真正提出该事项的人**，而非简单兜底成主持人。

### 2.3 解决方案

**方案 A：AI 智能识别（治本）**
- 在纪要生成 prompt 中增加「提出人」提取要求。
- 从转写文本里识别"X 提出…"、"按 X 的意见…"、"X 反映…"等线索，将 X 匹配到参会人。
- 无法识别时，proposer 留空（`null`），而非填 organizer。

**方案 B：表单去掉 organizer 兜底（治标，与 A 配合）**
- `generate/route.ts:77-96`、`meeting/[id]/page.tsx:1352-1354` 去掉 organizer 兜底。
- proposer 默认为空，强制用户在表单手选或由 AI 填。
- 补全 `batch/[id]`、`kanban`、`tracking` 三个表单缺失的「提出人」输入控件。

### 2.4 验收标准
- [ ] AI 能从会议转写中识别提出人，准确率 ≥70%（能识别的样本中）。
- [ ] proposer 为空时显示「待补充」而非自动填主持人。
- [ ] batch/kanban/tracking 三个表单均可输入提出人。

---

## 三、问题2：完成闭环（核心）

### 3.1 现状根因（已验证）

- 责任人可在「我的任务」标记完成并填完成说明（`mytasks/page.tsx:378-403`）。
- 完成数据写入 `hyzs_action_items` 表（`api/actions/[id]/route.ts:66-98`）。
- **但全仓无任何向提出人发通知的代码**——提出人只能被动翻台账。
- 现有推送通道方向都是「系统 → 责任人（催办）」，无反向「责任人 → 提出人（回执）」。

### 3.2 需求目标

形成 **A提出 → B执行 → A知晓（或 A验收）** 的完整闭环。

### 3.3 方案集（5 个，按复杂度递增）

> 以下方案可单选或组合，由评审决定。下表为对比概览，各方案详述见后。

| 方案 | 机制 | 提出人感知 | 成本 | 适用 |
|------|------|-----------|------|------|
| 方案1 | 企微消息通知 | 主动收到消息 | 低 | 快速达成闭环 |
| 方案2 | 站内消息中心 | 登录后查看 | 中 | 不依赖企微/免打扰 |
| 方案3 | 提出人验收 | 需点击确认 | 中高 | 严格质量管控 |
| 方案4 | 企微消息+验收 | 消息+确认 | 高 | 完整闭环 |
| 方案5 | 全部（分期） | 分阶段上线 | 最高 | 长期演进 |

---

### 方案1：企业微信消息通知 ⭐推荐起步

**机制**：责任人标记「已完成」并提交完成说明后，系统自动通过企业微信给**提出人**发一条应用消息。

**消息内容**：
```
【任务完成回执】
📌 任务：完成所有物料采购价格维护至系统
👤 责任人：廖新平
✅ 完成说明：价格已全部维护，详见附件截图
📎 证据：2 张图片
🔗 点击查看详情 → /mytasks?id=xxx
```

**触发时机**：`api/actions/[id]/route.ts` PUT 处理中，当 `status` 变为 `done` 时触发。

**技术实现**：复用现有 `lib/chat-client.ts` 的 `batchSendOAUserMessage`，消息目标改为 proposer 的 oaId。

**优点**：成本最低（复用现成推送能力），闭环最快达成，提出人无需登录系统即可收到。
**缺点**：消息单向，提出人无法在企微里直接回复/确认。

---

### 方案2：站内消息中心

**机制**：在系统内新建「消息中心」页面，提出人登录后看到待阅的完成回执列表。

**页面结构**：
- 路由：`/notifications`，侧边栏新增入口。
- 列表项：任务名 + 责任人 + 完成状态 + 时间 + 「查看详情」按钮。
- 未读红点：侧边栏「消息中心」图标角标。

**技术实现**：新建 `hyzs_notifications` 表（id/user_login_id/action_id/type/content/read/created_at），新建 `/api/notifications` 接口。

**优点**：不依赖企微/IM，可在任何环境使用；消息可结构化检索。
**缺点**：需提出人主动登录查看，时效性弱；增加一个表与一套接口。

---

### 方案3：提出人验收

**机制**：责任人不直接「完成」，而是「提交验收」；提出人在系统内点「通过」或「打回」才算闭环。

**状态流转**：
```
pending → in_progress → submitted（已提交验收）
                         ↓
              提出人「通过」→ accepted（已验收，闭环）
              提出人「打回」→ rejected（需重做）→ in_progress
```

**页面改动**：
- 「我的任务」责任人侧：完成按钮文案改为「提交验收」。
- 新增「我提出的」页面（proposer 视角）：列出待验收项，每项「通过/打回」按钮 + 备注框。

**技术实现**：action item 新增 `verify_status` 字段（submitted/accepted/rejected），新增 `/api/actions/[id]/verify` 接口。

**优点**：形成最完整的「提→做→验」链路，质量有把关。
**缺点**：增加提出人工作量；若提出人不及时验收，任务会卡在 submitted 状态；需超时自动验收机制。

---

### 方案4：企微消息 + 验收（组合）⭐推荐完整形态

**机制**：方案1 + 方案3 的组合。责任人提交验收 → 企微通知提出人 → 提出人点消息进系统验收。

**完整链路**：
```
B 提交验收 → 企微消息推送给 A（含「点击验收」按钮/链接）
           → A 点击进入「我提出的」页 → 点「通过」或「打回」
           → 通过则闭环；打回则企微通知 B 重做
```

**优点**：最完整的闭环，时效性（企微秒达）+ 质量管控（验收）兼具。
**缺点**：开发量最大；需处理超时、重复验收等边界。

---

### 方案5：全部实施（分期）

按阶段渐进上线，每期独立可用：

| 期 | 内容 | 目标 |
|----|------|------|
| 第一期 | 方案1（企微消息通知） | 最快达成「提出人知晓」 |
| 第二期 | 方案3（提出人验收） | 加质量管控闭环 |
| 第三期 | 方案2（站内消息中心） | 免企微依赖 + 历史检索 |

---

## 四、问题3：移动端支持

### 4.1 现状根因（已验证）

- 纯 Next.js Web，无 PWA、无小程序。
- **致命缺陷**：`layout.tsx` 缺 `export const viewport`，手机上按桌面宽度渲染并缩放，响应式全失效。
- 侧边栏抽屉是半成品（`dashboard-layout.tsx` 缺 translate 切换，固定 ml 挤压内容）。
- 已有大量响应式断点（51 处），但被 viewport 缺失掩盖。

### 4.2 方案集（4 个）

| 方案 | 成本 | 周期 | 复用率 | 体验 |
|------|------|------|--------|------|
| 方案A：响应式 Web 修复 | 低 | 短 | 100% | 中（浏览器/企微内嵌可用） |
| 方案B：PWA 可安装应用 | 中 | 中 | 100% | 中高（可装桌面，离线） |
| 方案C：微信小程序（另起工程）| 高 | 长 | 后端API复用，前端重写 | 高（原生体验，微信生态） |
| 方案D：响应式 + PWA（组合）| 中 | 中 | 100% | 中高 |

---

### 方案A：响应式 Web 修复 ⭐基础必做

**改动**：
1. `layout.tsx` 加 `export const viewport: Viewport = { width: 'device-width', initialScale: 1 }`。
2. `dashboard-layout.tsx` 修复侧边栏：移动端 `-translate-x-full lg:translate-x-0` + 去掉固定 ml。
3. 复杂表格页（tracking/project/[id]）移动端降级为卡片视图。

**优点**：成本最低，一次性修复让所有页面在手机可用；企微工作台内嵌也能用。
**缺点**：仍是网页，无原生体验，无法离线。

---

### 方案B：PWA 可安装应用

**在方案A基础上**：
1. 加 `public/manifest.json`（应用名/图标/主题色）。
2. 加 Service Worker（`next-pwa` 或手写）。
3. 静态资源缓存策略。

**优点**：可「添加到桌面」像 App 一样启动；支持离线访问已加载页面。
**缺点**：Service Worker 对动态数据（会议/AI接口）缓存复杂；iOS 对 PWA 支持有限。

---

### 方案C：微信小程序 ⭐用户期望

**目标**：用 Taro 或 uni-app 重写小程序端，后端 API 完全复用。

**工程结构**：
```
hyzs-miniapp/          新工程（Taro/React）
├── src/
│   ├── pages/          对应 Web 的核心页面
│   │   ├── mytasks/    我的任务（必做，移动端高频）
│   │   ├── meetings/   会议列表
│   │   ├── meeting-detail/  会议详情
│   │   ├── propose/    我提出的（配合闭环验收）
│   │   └── login/      企微授权登录
│   ├── services/       封装对 Web API 的调用
│   └── app.config.ts
└── project.config.json
```

**复用 Web 的部分**：
- 全部 `/api/*` 接口（RESTful，已完整）。
- 数据库、AI、OA、企微推送等后端逻辑。

**小程序独有改动**：
- 企微登录走小程序 `wx.login` 而非 OAuth 网页授权。
- 图片上传用 `wx.chooseImage` 替代 `<input type=file>`。
- 推送可用「模板消息/订阅消息」触达用户。

**优点**：原生体验；微信生态内一键打开；可推送；用户最熟悉。
**缺点**：前端基本重写（开发量最大）；需独立提审上线；受小程序能力限制（如录音转写需对接小程序录音 API）。

**技术选型建议**：**Taro 4 + React**（与现有 React 技术栈一致，降低学习成本）。

---

### 方案D：响应式 + PWA（组合）

先做方案A（响应式修复，立即可用），再加方案B（PWA 包装）。
适合「不上小程序但要移动端体验」的场景。

## 六、非功能需求

- **性能**：企微消息通知延迟 ≤5 秒；小程序首屏 ≤2 秒。
- **兼容**：响应式 Web 支持 iOS Safari / Android Chrome / 企微内置浏览器。
- **Hydration**：viewport 修复后，确保无 SSR/CSR 不一致。
- **权限**：闭环通知只发给 proposer（且 proposer 不为空）；验收只允许该 action 的 proposer 操作。
- **数据迁移**：proposer 字段已有，无需迁移；`verify_status` 新增列需 ensureColumn 迁移。
