# OA 绩效改善项（GSMALT）并入行动项体系 需求说明

> 版本：v0.2（评审中，6 项决策已确认）
> 创建：2026-09-05
> 状态：待评审

---

## 一、背景

目前系统的行动项全部来自**会议纪要**（会议 → 行动项）。但 OA 里还存在一套"绩效改善行动项"，存放在泛微 OA 的 **`uf_GSMALT`（主表）+ `uf_GSMALT_dt1`（明细）** 中——每行明细就是一条改善行动项（含责任人、行动内容、节点、原因分析、KPI）。

这些改善项目前**不在系统行动项体系内**，无法在系统里做"待办处理 / 统计 / 看板展示"。

**目标**：把 OA 的 GSMALT 改善行动项**并入系统行动项体系**，统一管理、统一跟踪、统一统计，让责任人在系统一处处理。

## 二、已确认决策（2026-09-05）

| # | 决策 | 结论 |
|---|------|------|
| 1 | 同步范围 | **先最近 2 个数据月**（当前为 2026-07、2026-08），随月份推进增量 |
| 2 | 已稽核项处理 | **按 OA 当前稽核结果导入**：V→已完成、X→未完成、0→待定、空→未处理 |
| 3 | 统计 | **需要统计**，展现方式见「五、统计与展现规划」 |
| 4 | 回写 | **不回写 OA**；在会议助手内完成处理与统计 |
| 5 | 字段口径 | 内容/原因取 **`xdjh2` / `yyfx2`**（与现有 /api/gsmalt 一致） |
| 6 | 可见范围 | 大前提不变：责任人只能看到**自己提出、或责任人是自己**的项；admin/manager 全量 |

## 三、目标与用户故事

| 角色 | 诉求 |
|------|------|
| 责任人 | 待办里看到"绩效改善项"（我的/我提的），处理、填进展、标记完成 |
| 管理者/老板 | 看绩效改善项完成情况、责任人表现、超期、按 KPI/部门分布 |

## 四、范围

### 4.1 纳入
- 从 OA `uf_GSMALT` + `uf_GSMALT_dt1` **同步生成**系统行动项（来源打标）
- 字段映射：内容(xdjh2)、责任人(zrr)、责任部门(zrbm)、节点(jd)、原因(yyfx2)、KPI(clzbkpi)、稽核(jh)
- 责任人在「我的任务/待办中心」处理，**不回写 OA**
- 统计与展现（见五）
- 同步触发：admin 手动按钮 +（可选）每日定时增量

### 4.2 不纳入
- 不回写 OA（系统处理结果不反向同步）
- 不改变 OA 表单/稽核逻辑
- **不参与系统"到期自动打X+转派"**（避免与 OA 稽核节奏冲突）——见「八、待最后确认」
- 历史超早数据不补导（近 2 个数据月）

## 五、数据来源与字段映射

**数据源**：`[FWsv].[ecology]` 的 `uf_GSMALT`（主）+ `uf_GSMALT_dt1`（明细），翻译表：
- `hrmresource`（责任人内码→姓名）、`hrmdepartment`（部门内码→部门名）、`uf_KPI`（KPI 内码→名称）

**逐条映射**（一条 dt1 = 一条行动项）：

| OA 字段 | 含义 | 映射系统 |
|---------|------|---------|
| `uf_GSMALT_dt1.id` | 明细行主键 | **同步键**（幂等/增量依据，存来源ID） |
| `mainid` | 所属主单 | 来源关联 |
| `xdjh2` | 行动计划 = 任务内容 | description |
| `zrr` → 姓名 | 责任人 | owner |
| `zrbm` → 部门名 | 责任部门 | dept |
| `jd` | 计划完成节点 | due_date（date 型） |
| `clzbkpi` → KPI 名 | KPI | 备注/元数据 |
| `yyfx2` | 原因分析 | 备注/元数据 |
| `jh` | 稽核 0=V 1=X 2=0 空=未 | 导入映射：V→done, X→blocked, 0→待定, 空→pending |

**幂等**：以 `dt1.id` 为唯一键，重复同步不新增；OA 改内容/节点 → 覆盖更新对应系统项（删除的行保留系统侧，不自动删）。

## 六、统计与展现规划

GSMALT 改善项与会议行动项是两套不同口径，**统计独立成板块**，不与"会议产出完成率"混算，避免口径混淆。

### 6.1 责任人视角（我的待办）
- 我的改善项按"数据月/待办/已完成/未完成"分组展示
- 能直接处理：标记完成 / 填进展；可看到每条的节点、KPI、是否超期

### 6.2 管理者视角（绩效改善总览，放在**月度看板**内新增板块）
- **总览卡**：本月改善项总数 / V 已完成 / X 未完成 / 0 待定 / 未稽核（未处理）/ 完成率（完成 ÷ 有稽核，或按口径）
- **责任人排行**：按人 → 数量、完成率、未完成数、超期数（一眼看出谁没跟上）
- **KPI 分布**：改善项主要针对哪些 KPI，各 KPI 完成情况
- **部门分布**：按部门看改善项数量与完成率
- **月度趋势**：近几个月"改善项总数 / 完成率"走势
- **超期清单**：节点已过仍未完成的改善项

### 6.3 统计口径（建议）
- 按月统计：按 **节点日期(jd) 所在月** 归属（与现有 /api/gsmalt 一致）
- 完成率 = 该月 V(完成) 条数 ÷ 该月有稽核(非空)条数；未稽核单列"未处理"，不计入分子分母（与现有稽核口径一致）
- X(未完成) 与 0(待定) 都算"未完成/待处理"，可分开展示

### 6.4 展示载体
- 新增/强化**月度看板「绩效改善」板块**
- 台账、待办、贡献榜等**不做**改善项混入（避免污染现有会议项口径）；如需在台账查看，加来源筛选（可选）
- 明细下钻：总览 → 责任人 → 该人改善项明细（逐条）

## 七、页面/交互改动

1. 同步管理（admin）：预览待导入/变更条数 → 执行 → 同步日志
2. 我的任务/待办中心：改善项带来源标识，可处理
3. 月度看板「绩效改善」统计板块（见六）
4. 可选：台账来源筛选

## 八、权限

- 同步：admin
- 查看/处理：责任人本人（自己提出或责任人是自己）+ 具备月度看板权限者（admin/manager/secretary）
- 普通用户不开放手动导入

## 九、同步流程（草案）

```
admin 点"同步 OA 绩效改善项"（或每日定时）
  → 读 OA uf_GSMALT + dt1（翻译责任人/部门/KPI，按 jd 近 2 月过滤）
  → 与系统内"来源=gsmalt"按 dt1.id 比对
  → 新增：生成行动项（pending；有稽核则按 jh 置 V/X/0）
  → 变更：更新内容/节点/责任人（已稽核的项状态以 OA 为准覆盖）
  → 预览 → 执行 → 记同步日志
```

> 覆盖策略注意（待最后确认 2）：OA 稽核值 `jh` 为空的项，若责任人在系统里已标记完成，**下次同步不要把 OA 空值覆盖掉系统的完成**——只同步 OA 非空稽核，系统已处理而 OA 空的保留系统结果。

## 十、风险与对策

| 风险 | 对策 |
|------|------|
| 责任人姓名/部门 OA 与系统映射不一致 | 复用 `resolveActionOwnerIdentity`，映射不到进"待处理"清单告警 |
| 与会议行动项重复 | 来源标记区分，不自动合并 |
| 大量历史 | 近 2 月，可配置 |
| OA 行被改/删 | 同步键幂等；删除行保留系统侧 |
| 双轨稽核冲突（OA jh vs 系统处理） | 明确不回写 + 同步只以 OA 非空稽核覆盖（见九备注） |

## 十一、验收标准

- [ ] admin 预览+执行同步，生成改善项（责任人/内容/节点正确，稽核沿用 OA）
- [ ] 同一 dt1.id 重复同步不产生重复项
- [ ] 责任人在待办看到并能处理自己的改善项（含我提出的）
- [ ] 普通员工看不到别人的改善项
- [ ] 月度看板「绩效改善」板块统计正确（总数/V/X/0/完成率/超期/排行）
- [ ] 同步日志可追溯
- [ ] 不影响既有会议行动项任何功能

## 十二、待最后确认

1. **是否对该来源项做"到期前提醒"**：默认**不做**（与会议行动项分开节奏，避免 OA 还没稽核就系统先催）；要催可单独配。
2. **OA 空稽核 + 系统已处理的覆盖策略**：确认"OA 只同步非空稽核、系统已处理不被 OA 空值覆盖"。
3. 管理者/老板看改善项统计放在**月度看板新增板块**，是否够？（也可放周看板/单独页，二选一）
4. 需不需要"我提出的"也纳入我的待办可处理？（决策 6 说可见，若我提出但责任人是别人，通常不处理——默认只"责任人是我的"可处理，"我提出的"仅可见。）

## 十三、工期估计

需求确认后：同步引擎 + 管理页 + 待办/台账来源标识 + 月度看板统计板块 + 自测 ≈ **3~4 天**。
