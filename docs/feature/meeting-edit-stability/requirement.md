# 会议行动项编辑稳定性与归档数据一致性修复 需求文档

> 版本：v1.0  ·  状态：规划中（待评审）
> 涉及：会议详情页行动项/纪要编辑、行动项存储双写（会议JSON + SQL Server 台账）、归档流程
> 关联代码：`meeting/[id]/page.tsx`、`api/meetings/[id]/route.ts`、`lib/minutes-derive.ts`、`storage/database/action-storage.ts`

---

## 一、背景与两大问题

用户操作路径「创建会议 → 生成行动项 → 手动输入内容 → 归档」中存在两个缺陷，已定位到代码根因：

| 问题 | 一句话描述 | 现状根因 |
|------|-----------|---------|
| 问题1 输入乱跳 | 编辑行动项/纪要时输入焦点丢失、内容被重置、页面滚动跳动 | 行动项 id 三级跳变导致整行 remount + 保存后全量替换列表 + 编辑态被外部数据回写覆盖 |
| 问题2 归档后内容消失 | 归档（锁定版本）后重新加载，部分行动项不见了 | 保存纪要时行动项被"重新派生+物理删除"；JSON 与 DB 双写不一致；GET 时 DB 优先二选一丢弃 JSON-only 项 |

---

## 二、根因明细（已验证）

### 2.1 问题1：输入乱跳

| 编号 | 根因 | 位置 |
|------|------|------|
| R1 | 行动项 id 三级跳变：`new-时间戳` → `rd-时间戳`（无 dbId）→ `dbId`，行 key 用 `item.id`，key 变即整行卸载重建（焦点丢失、滚动跳动） | `page.tsx:1498`、`route.ts:370`、`page.tsx:1079`、`page.tsx:2227` |
| R2 | 新增项首次保存后，用服务端返回列表**全量替换** `actionItems`，所有行引用变化叠加 key 跳变 | `page.tsx:1447`、`page.tsx:1479` |
| R3 | `MeetingMinutesBlock` 监听 `[minutes]` 引用变化即整体重置本地编辑态（含强制退出 Markdown 编辑），正在输入的内容被服务端旧数据覆盖 | `page.tsx:519-523` |
| R4 | `InlineEdit`（contentEditable）的 `useEffect([value])` 直接覆写 DOM，异步回写期间光标被重置 | `page.tsx:348-353` |
| R5 | 每次键击 `JSON.parse(JSON.stringify(data))` 深克隆整棵纪要树，大文档卡顿加剧视觉跳动 | `page.tsx:529-536` |
| R6 | 临时 id 用 `Date.now()`，连续快速新增/复制可能撞 key | `page.tsx:1498`、`page.tsx:1521` |

### 2.2 问题2：归档后内容消失

| 编号 | 根因 | 位置 |
|------|------|------|
| R7 | **保存纪要即重派生**：PATCH 带 `minutes` 时行动项仅从 `minutes.actionTable` 重新派生，与旧项按"序号/描述前30字"模糊匹配，**匹配不上的直接丢弃**（手动新增、改过描述的项最易命中）；随后 sync 把 DB 中不在新列表的行**物理删除**。摘要 Tab 行内编辑失焦也会触发该 PATCH | `route.ts:466-500`、`route.ts:93-101`、`page.tsx:2086-2099` |
| R8 | 派生合并白名单不含 `dueDateType/proposer/priority`，派生值覆盖手动值 | `route.ts:476-477` |
| R9 | `addActionItem` 先写会议 JSON 再写 DB，**DB 失败不回滚**（注释称事务实际没有）→ 产生仅存在于 JSON 的项；DB 写入 status 硬编码 `pending` 与前端 `confirmed` 不符 | `route.ts:374-418` |
| R10 | GET 时 `dbActionItems.length > 0` 则**只返回 DB 行**，JSON-only 项被丢弃；归档后 `loadMeeting()` 立即触发该 GET，使丢数恰在"归档"操作后暴露 | `route.ts:306-321`、`page.tsx:1273` |

## 三、需求目标

1. **编辑不跳**：行动项、纪要的任何行内编辑过程中，焦点不丢失、内容不被外部回写覆盖、页面不发生非预期滚动。
2. **数据不丢**：手动新增/编辑过的行动项，在保存纪要、归档、重新加载后一律不消失；字段值不被派生逻辑意外覆盖。
3. **双源一致**：会议 JSON 与 `hyzs_action_items` 台账对同一行动项保持一致，单一写入失败可恢复、可感知。
4. **向后兼容**：不影响已归档会议的 OA 推送、「我的待办」过滤、持续项推送等既有链路。

## 四、解决方案（按修复点拆分）

### 修复1：行动项标识稳定化与局部更新（对应 R1/R2/R6）⭐ P0

**方案**：
- `addActionItem` 接口改为**返回单条新创建的行动项**（含 `dbId`、`originalId`），前端只用该条**替换对应的 `new-*` 临时行**，其余行不动（消除全量替换）。
- 前端临时 id 改用自增序号 + 随机段（`new-{seq}-{rand}`），消除 `Date.now()` 撞 key。
- React key 改用稳定值：`item.dbId ?? item.originalId ?? item.id`，保证同一行在「新增 → 保存 → 重载」全程 key 不变。
- `mapActionItems` 与 GET 接口统一 id 口径（`dbId` 优先），`rd-*` 与 `dbId` 不再交替出现。

### 修复2：保存纪要不再物理删除手动行动项（对应 R7/R8）⭐ P0

**方案 A（推荐）：派生只做"更新匹配项 + 追加新项"，绝不删除**
- `minutes` PATCH 派生时，匹配得上的旧行仅更新纪表格内的字段（描述/负责人/日期），手动字段（提出人、优先级、截止类型、状态、OA 回传字段）全部保留；
- 匹配不上的**现有项一律保留**（视为用户手动维护的台账）；纪要中出现而台账没有的才新增；
- `syncActionItemsToDatabase` 的删除分支仅在该行被前端显式 `deleteAction` 时触达（删除走既有 `DELETE /api/actions/[id]`），纪要保存路径不再删除。

**方案 A 的折中删除规则（防陈旧项累积）**：
- 仅"纯派生来源且零手动编辑"的项（无 owner 手填、无状态流转、无 OA 回传）允许随纪要表格删行联动删除；
- 任何被手动新增/编辑过的项（含手动项、改过描述的派生项）**永不自动删除**，只能走行动项 Tab 显式删除；
- 联动删除发生时在保存结果中提示"已随纪要移除 N 条派生项"。

**方案 B（保守替代）：`minutes` PATCH 完全不再派生行动项**，仅派生摘要；行动项只由「生成」和手动操作维护。
- 优点：最简单，零误删风险；缺点：纪要表格内手工改动不再回流到行动项，需用户手动同步。

> 评审决定 A 或 B。默认按 A（含折中删除规则）实施。

### 修复3：JSON/DB 双写一致性（对应 R9/R10）⭐ P0

- `addActionItem` 调整写入顺序：**先写 DB，成功后再写会议 JSON**；写入前按 `originalId` 做**幂等检查**（`getActionItemByMeetingAndOriginalId`），防重试产生重复行；DB 失败直接返回错误，前端保留临时行并提示重试（不再产生 JSON-only 项）。JSON 更新失败仅降级为警告不判失败（DB 为 GET 主源），并留日志。DB 写入 status 采用前端传入值（`confirmed`），不再硬编码 `pending`（已核实 `pending/confirmed` 在企微推送、待办、助手统计中待遇相同，无连锁影响）。
- GET 合并逻辑由「DB 有则只看 DB」改为**并集合并**：以 DB 为主（`cancelled` 已被存储层默认过滤，已删项不会复活），JSON-only 项（历史遗留）按 `originalId`/描述去重后补入，保证加载即可见；**对 JSON-only 项做惰性回填**（首次编辑时创建对应 DB 行），否则该项 PUT/DELETE 会 404 无法编辑。服务端日志标记分歧行便于排查。

### 修复4：编辑态保护（对应 R3/R4/R5）⭐ P1

- `MeetingMinutesBlock` 的外部重置 effect 增加 `if (!dirty)` 守卫：本地有未保存编辑时不重置；保存成功后显式同步一次并保序。保存前对比会议 `updated_at`，与服务端分歧行提示冲突（防覆盖他人并发修改）。
- 监听会议 `status → locked`（他人归档）时，强制退出本地编辑态并提示"会议已被归档"，避免锁定后页面仍显示可编辑态。
- `InlineEdit` 仅在**非聚焦**状态覆写 DOM（记录 `document.activeElement` 对比），聚焦期间跳过外部覆写。
- `upd()` 深克隆改为结构化局部更新（或 `structuredClone` + 路径级浅拷贝），大文档键击不再全量克隆。

### 修复5：可观测性（配套）⭐ P2

- 行动项 sync/删除/合并处增加结构化日志（meetingId、actionId、动作、来源），线上再出现"消失"可在日志定位是哪条链路删的。

## 五、用户故事

- 作为**会议记录人**，我在行动项表格里逐项填写负责人/日期时，光标不应跳动、已填内容不应被重置，我可以连续流畅地录完所有项。
- 作为**会议记录人**，我手动新增的行动项，在保存纪要、锁定归档、刷新页面后依然存在，字段值保持我填的样子。
- 作为**会议记录人**，我在 Markdown 模式编辑纪要时，后台录音结束/他人保存不会清掉我正在输入的内容。
- 作为**系统管理员**，任何行动项的删除都有日志可查，我知道它是什么时候、被哪条链路删的。

## 六、功能范围

**含**：
- 会议详情页行动项表格的行内编辑、新增、复制、删除交互修复。
- 纪要保存（含摘要行内编辑触发的 PATCH）与行动项台账的同步策略修复。
- `GET/PATCH /api/meetings/[id]`、`PUT/DELETE /api/actions/[id]` 的 id 口径与合并逻辑修复。
- 历史遗留 JSON-only 行动项的加载可见性（并集合并）。

**不含**：
- 归档/解档的 OA 推送流程本身（`lock/route.ts` 不动）。
- 「我的待办」「持续项推送」按归档状态过滤的业务规则（设计如此，保留）。
- 行动项表结构变更（无新增列，无需迁移）。
- 移动端/小程序适配（见 action-lifecycle 需求）。

## 七、数据来源与影响面

| 数据源 | 用途 | 改动 |
|--------|------|------|
| 会议 JSON（`hyzs_meetings` 内容字段） | 会议详情、纪要、行动项快照 | 派生/合并逻辑修改，存储结构不变 |
| `hyzs_action_items` 台账 | 行动项持久化、我的待办、OA 推送源 | 删除分支收紧、新增写入顺序调整，表结构不变 |

**影响接口**：`GET/PATCH /api/meetings/[id]`、`POST/DELETE /api/meetings/[id]/lock`（行为不变，仅受益）、`PUT/DELETE /api/actions/[id]`。

## 八、交互需求

- 行内编辑（描述/提出人/负责人/日期/优先级）全程不丢焦点。
- 新增行动项后立即编辑，保存瞬间该行不闪、不滚动跳变。
- 保存失败（网络/DB）时保留用户输入并给出提示，不静默吞错（现状 `catch {}`）。
- 锁定归档成功后的提示信息保持现状（OA 推送结果汇总）。

---

## 九、入口与权限

- 入口不变：会议详情页 `/meeting/[id]`（行动项 Tab、纪要 Tab、摘要 Tab）。
- 权限不变：沿用现有会议编辑权限判断；接口侧无新增鉴权点。

---

## 十、非功能需求

- **性能**：100+ 行动项、万字纪要下，键击到渲染 ≤100ms（无全量深克隆）。
- **一致性**：同一行动项在「会议 JSON / 台账 / 前端列表」三处 id 与字段一致；一次操作后不产生孤儿行。
- **可回溯**：删除类操作全部留日志（who/when/which）。
- **兼容**：不影响已归档会议数据；历史 JSON-only 项加载可见后可正常编辑并入台账。

## 十一、验收标准

**问题1（乱跳）**
- [ ] 新增行动项 → 立即在描述栏连续输入 → 首次失焦保存 → 光标/内容/滚动位置无变化，该行不重挂载（React key 全程不变）。
- [ ] 连续快速点击"新增""复制"3 次以上，不出现 key 冲突告警。
- [ ] Markdown 模式编辑纪要期间另一端保存同一会议，本地编辑内容不被覆盖、不退出编辑模式。
- [ ] 责责人/提出人选择器异步回写时，正在编辑的描述输入框光标不丢。

**问题2（消失）**
- [ ] 生成行动项后手动新增 2 条 → 编辑纪要并保存 → 手动新增的 2 条仍在，且提出人/优先级/截止类型保持手填值。
- [ ] 摘要 Tab 行内编辑失焦（触发 minutes PATCH）→ 行动项无任何减少。
- [ ] 锁定归档 → 刷新页面 → 行动项数量与归档前一致。
- [ ] 构造 DB 写入失败（如停库）新增行动项 → 前端提示失败、临时行保留，恢复后重试成功且不产生重复行。
- [ ] 历史遗留 JSON-only 项（修复前产生）打开会议即可见。

## 十三、风险与对策（连锁影响评估）

| 修复点 | 连锁影响 | 评估结论 | 对策 |
|--------|---------|---------|------|
| 修复2 方案A | 纪要表格删行不再联动删除行动项 → 陈旧项累积 | **行为变化，需用户知晓** | 折中删除规则（纯派生+零编辑项可联动删）；保存结果提示移除数量 |
| 修复3 先写 DB | DB 成功、JSON 失败 → 重试产生重复行 | 真实风险 | 按 `originalId` 幂等检查；JSON 失败降级警告（DB 为 GET 主源） |
| 修复3 GET 并集 | 历史 JSON-only 项可见但无法编辑（PUT/DELETE 404） | 真实风险 | 惰性回填：首次编辑时创建 DB 行 |
| 修复3 status 确认值 | `pending → confirmed` 是否影响下游 | **已核实安全**：企微推送 ACTIVE_STATUSES、待办、助手统计均含两者 | 无需额外处理 |
| 修复3 并集 | 已删除项（cancelled）复活 | **已核实安全**：存储层默认过滤 cancelled | 无需额外处理 |
| 修复1 id 口径 | 其他页面（batch/kanban/tracking/mytasks）调用兼容性 | **已核实安全**：PUT/DELETE 已有 originalId 回退查找 | 无需额外处理 |
| 修复4 dirty 守卫 | 并发编辑由"外部覆盖用户"变为"用户可能覆盖外部" | 方向性变化 | 保存前 `updated_at` 版本对比 + 分歧提示 |
| 修复4 锁定+dirty | 归档瞬间本地仍显示可编辑 | 边缘场景 | 监听 status→locked 强制退出编辑态 |
| 全局 | `getAllActionItems` 15 秒列表缓存（action-storage.ts:391-399），写路径漏失效缓存 → "删了还在/加了不显示" | 实现级风险 | 实现清单固定：所有写路径后调用 `invalidateListCache()` |
| 数据层面 | 历史已被物理删除的行动项无法恢复 | **无法修复，需预期管理** | 并集仅能救回 JSON 残留项；DB+JSON 均被删的需手工重录 |
