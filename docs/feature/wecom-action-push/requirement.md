## 1. 背景

### 1.1 现状链路（保持不动）

会议锁定时现有 4 路推送，**全部保留、一行不改**：

```
会议锁定(归档)
   ├─#1 OA表同步    → OA uf_meetingplan（行动项数据落库，增删改差分）
   ├─#2 归档通知    → 自研IM（参会人+主持人）
   ├─#3 归档通知    → 企微直连（应用1000043，首次归档，已有）
   └─#4 待办清单    → 自研IM（责任人）+ 每日 09:00/17:30 定时推
```

### 1.2 本期目标（并行叠加，不替换）

在现有推送基础上，**新增企微直连待办通道**：行动项推送到企业微信，责任人在企微里可直接填写，结果回写本系统。

- OA 不停写（`uf_meetingplan` 继续同步，作为兜底与周转型数据）
- 自研 IM 不动（归档通知 + 待办清单照常）
- 企微通道纯增量：开关关闭即完全回到现状，零回退风险

### 1.3 企微消息能力约束（选型依据）

| 企微通道 | 撤回 | 修改已发内容 | 结论 |
|---|---|---|---|
| text / textcard / markdown | ❌ 无 | ❌ 无 | 变更再发会**消息叠加刷屏**，旧卡片残留 |
| taskcard + update_task_card | ❌ | ⚠️ 仅能更新按钮状态，正文不可改 | 只适合"点击后标记已处理"场景 |
| **应用待办 apptodo（create_todo / finish_todo）** | 不需要 | ✅ 同 `todo_code` 再次调用为 **upsert 更新**，待办中心始终显示最新 | **增删改查的正解，选为主通道** |

> 兜底：textcard 链接指向实时页面，点旧卡片看到的数据仍是最新的，信息不会错，只是消息流有历史残留。

## 3. 核心流程

### 3.1 流程一：锁定 → 并行推送（主链路）

```
会议编辑完成
    │
    ▼
点击「锁定版本」────────────────────────────────────────────┐
    │                                                      │
    ▼                                                      │
生成版本快照 v(n)                                           │
    │                                                      │
    ├──► #1/#2/#4 现有推送（原样执行，不动）                    │
    │                                                      │
    ▼                                                      │
┌─ 新增：企微推送引擎（与现有推送并行） ──────────────┐         │
│ 1. 取本版本全部行动项                    企微API失败 │         │
│ 2. resolveUserIdsByNames: 姓名→企微userid  ──降级──► │ 记录失败│
│ 3. 按责任人分桶                                  │ 不阻断归档│
│ 4. diff 对比该责任人上次已推送内容（见3.3）          │         │
│ 5. 逐人执行待办 upsert + 必要时发汇总卡片           │         │
│ 6. 记录推送快照 + 日志                            │         │
└──────────────┬───────────────────────────────────┘         │
               ▼                                           │
    重复锁定：幂等跳过（同 meetingId+version 已推送）           │
               │                                           │
               ▼                                           │
           归档完成 ◄───────────────────────────────────────┘
```

```

               └──► 展现层实时刷新（M4）
```

### 3.3 流程三：增删改查同步（关键设计）

**版本语义**：解锁 → 修改 → 再锁定 = 新版本 v(n+1)。推送引擎对"每个责任人上次已推送内容"做 diff，只同步变化。
**防刷屏原则**：变更一律通过**待办 upsert 原地更新**（同 `todo_code`），不新发消息；textcard 仅锁定且有实际增删改时发一条汇总。

| 场景 | 触发条件 | 系统动作 | 责任人在企微看到 |
|------|---------|---------|----------------|
| **增** | 新版本新增行动项 | `create_todo` 新建待办 | 待办中心多一条新待办（不进聊天流） |
| **删** | 行动项从新版本移除 | 本系统标记 `cancelled`；`finish_todo` 取消待办 | 待办从列表消失/标记取消，聊天流无打扰 |
| **改** | 描述/责任人/截止日/优先级 变更 | diff 命中 → 同 `todo_code` 再调 `create_todo` **原地更新** | 待办内容/截止日静默变为最新，**不产生新消息** |
| **查** | 责任人随时打开待办中心/汇总卡片 | OAuth 直达 mytasks 页 | 实时全量待办清单（不依赖推送） |
| **转派** | 责任人变更 | 旧责任人 `finish_todo` + 新责任人 `create_todo` | 双方待办列表各自增/删 |
| **已填写保护** | 该项已有完成说明且已提交 | 不同步、不覆盖（对齐 OA wcjgsm 保护语义） | 待办已标记完成，无打扰 |
| **重新激活** | 曾取消的项又出现在新版本 | 清除 cancelled 标记，`create_todo` 重建 | 待办重新出现 |
| **完成** | 用户填写完成说明提交 | 待办标记完成 + textcard 回执（可配置关闭） | 「已收到：xxx 已完成 ✅」 |

**同步判定流程：**

```
新版本锁定
    │
    ▼
逐条对比上次推送快照（按 task_id = meetingId__itemId）
    │
    ├── 快照中不存在 ──────────────► [增] create_todo 新建待办
    ├── 本次不存在 + 未填写 ────────► [删] finish_todo 取消待办
    ├── 本次不存在 + 已有完成说明 ──► 保留存档，不动待办（保护）
    ├── 字段有差异 + 已有完成说明 ──► 跳过（保护）
    ├── 字段有差异 + 未填写 ───────► [改] create_todo 原地 upsert（无新消息）
    └── 无差异 ──────────────────► 跳过（幂等）
    │
    ▼
本次有任一增/删/改 → 给涉及责任人发一条 textcard 汇总（N 条新待办 / M 条已更新）
本次无任何变化 ────► 不发任何消息
```

## 4. 功能需求明细

### M1 推送引擎

| 编号 | 需求 | 说明 |
|------|------|------|
| M1-1 | 锁定自动触发 | lock 接口内调用，与现有 #1/#2/#4 推送**并行**，互不影响 |
| M1-2 | 按责任人分桶 | 待办天然按人维度；textcard 汇总一人一条 |
| M1-3 | diff 增量 | 维护"每人每会议最后推送快照"，仅同步增/删/改 |
| M1-4 | 降级策略 | 企微 API 失败不阻断归档，记录失败日志，支持手动重推 |
| M1-5 | 持续项/行动项区分 | 待办 summary 前缀/描述中区分（沿用 `item_type` 语义） |
| M1-6 | 总开关+白名单 | `WECOM_TODO_PUSH_ENABLED` 总开关；沿用 `WECOM_TEST_MODE`+白名单灰度 |
| M1-7 | 防刷屏约束 | 变更只走待办 upsert，聊天流消息（textcard）仅在锁定且有实际增删改时发一条 |

|------|------|------|

| M2-3 | 取消/恢复 | 本系统字段记录（`cancelledAt`），不动 OA 侧 `HYZS_CANCELLED` |

## 6. 非功能需求

1. **零侵入**：现有 #1/#2/#4 推送通道与 OA 表同步一行不改；本期为纯增量
2. **归档不阻断**：企微推送（含 API 失败/超时）不影响锁定/归档主流程与现有推送
3. **性能**：企微推送与现有推送并行执行，归档接口总耗时增加需 ≤3s（超时熔断）
4. **幂等**：同版本重复锁定不重复推送、不重复建待办
5. **回退**：关闭 `WECOM_TODO_PUSH_ENABLED` 即完全回到现状，无残留影响
6. **安全**：待办/卡片链接仅 OAuth 登录用户可访问；填写接口校验 session 身份与责任人一致
7. **移动端适配**：填写页按企微内置浏览器优化（现有响应式基础已具备）

## 7. 不含（本期不做）

- OA `uf_meetingplan` 停写（保留双写，待企微通道稳定后另出计划）
- 自研 IM 任何改动（归档通知、待办清单、定时推送全部原样）
- 到期自动提醒机器人（复用现有 continuous-push 机制另行迭代）
- taskcard + update_task_card（按钮态更新）：若 apptodo 权限申请受阻，作为备选通道再评估

## 8. 验收标准（摘要）

1. 开关开启时锁定会议：责任人在企微待办中心 1 分钟内出现其名下待办，涉及变更者收到一条汇总卡片；重复锁定不重复收到
2. 新版本分别增/删/改各 1 条 → 待办中心相应**新增/消失/原地更新**，聊天流至多多一条汇总通知，**旧消息无叠加刷屏**
3. 企微点待办链接 → 免密登录 → 只看到自己名下待办 → 提交完成说明 → mytasks/看板即时可见，来源标记"企微"，待办标记完成
4. 已填写项在新版本同步中被跳过，不被覆盖
5. **现有通道回归**：开关任意状态下，OA 表同步、IM 归档通知、IM 待办推送行为与改造前完全一致
6. 关闭企微配置开关 → 企微侧无任何新消息/待办，系统回到现状
